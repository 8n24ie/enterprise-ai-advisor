# 最小试点、验收与行动方案

本文件是用户确认框架的操作化说明；示例和计算方法属于设计建议，不伪称来自 PDF。

## 七项试点要素

| 要素 | 写清什么 |
|---|---|
| 验证目标 | 一次主要判断，例如是否在保持重要字段质量的前提下减少整单处理时间 |
| 范围 | 岗位、任务、材料类型、业务环节；暂不包含什么 |
| 输入与输出 | 来源、权限、版本、格式；使用者收到什么可复核结果 |
| 职责 | 人、AI、普通程序处理哪些步骤；没有某类角色就直说无需它 |
| 异常处理 | 缺数据、冲突、识别不确定、规则不匹配、系统失败时如何标记、回退与复核 |
| 负责人及投入 | 谁执行、谁评价、谁决定；时间、费用与人工投入上限；未确认者明确标记 |
| 验收与决策 | 比较方法、主要指标、必要约束、观察局限，以及继续、调整、停止和证据不足的条件 |

缺关键前置条件时可以给暂定设计，但不能表述为已能启动。一个人的省时可能增加另一个人的复核负担，职责与投入须合起来看。明确规则交给普通程序；可建议人工或现有系统先跑通试验，原型不必等于开发新软件。

## 验收设计

选一个主要成效指标，再加必要的质量和成本约束，避免堆砌指标。

- **质量**：按照业务错误类型检验；重要错误单列，不能被总体准确率掩盖。必要时区分漏报、误报、字段正确与整单可用。
- **效率**：区分人员实际投入与端到端经过时间。记录准备、整理、等待、执行、审核、返工。等待影响交付时效，但不能把所有等待都当成人工工时相加。
- **使用情况**：看代表使用者能否完成任务、是否持续使用、放弃原因及额外步骤；不能只数打开次数。
- **实际投入**：一次性整理与搭建、持续复核、维护、工具费用分别列出。没有基准工作量、单价或试验数据时，不给确定预算与回本期限。

可用计算形式（变量都需要来源）：

> 单任务人员净节省（人时） = 旧流程各角色实际工时之和 − 新流程各角色实际工时之和。
>
> 观察期总人时（人时） = 一次性准备工时 + 观察期操作、审核、返工及维护工时；按每位参与者的实际工时加总。
>
> 观察期现金费用（元或注明的币种） = 工具费用 + 其他有依据的实际现金支出；分项列出。
>
> 仅在存在明确换算依据时：折算总成本（元） = Σ（各岗位工时 × 对应且注明来源的小时成本）+ 未包含在上述小时成本中的现金费用。

没有明确小时成本及适用口径时，并列报告“总人时”和“现金费用”，不直接相加、不虚构单价或称为已算出总成本。已有换算依据时说明岗位、单价来源、币种及覆盖范围，避免现金支付的人工费或工具费在费率与支出中重复计入。不要把已经计入人工的整理或审核重复扣减；新增收入、避免损失和释放工时分别报告。

### 比较方法先于目标数字

1. 明确基线如何取得。无基线时先记录旧流程，或选择复杂度相近的任务比较；不虚构“原来平均耗时”。
2. 样本覆盖正常、重要异常和边界；说明数量、选择理由与局限。开发调试用过的样例与验收样例分开，没有合理样本量依据时标为探索性试验，不宣称统计证明。
3. 明确谁评价、依据是什么、如何处理评价分歧。已知的人和标准直接复用。
4. 把**已确认目标、建议目标、待测量事项**分开。用户给定阈值不得默默改成更易通过的数字；不合理或冲突时指出取舍。
5. 说明观察期限及局限，短期节省不自动等于长期收益。

### 投入与退出

提前写出投入上限和暂停条件。上限尚未给出时标为启动前待确认，不自行编造额度，也不把咨询变成反复审批。

- **继续或有限扩大**：主要目标与必要约束达到，数据足以支持；说明扩大到哪一小步及新增依赖。
- **调整后再试**：有证据指出可修正的失败机制；列出改动、下一次观察及剩余投入，不默认加钱或延期。
- **停止当前方案**：重要错误、价值不成立、无法解决的前置障碍，或达到停止条件。
- **证据不足**：材料、样本或观察期不足；说清缺什么及是否值得在既定上限内补测。

到达上限就暂停，不默认继续。Skill 提供证据和建议，项目负责人决定是否扩大、追加投入或停止。

## 已有项目的修复实验

优先检查造成差距的步骤：资料与口径 → 模型处理 → 规则与集成 → 人工审核 → 入口与使用。按证据选择，不机械全查。

使用“怀疑的原因 → 拟作改动 → 观察结果 → 推翻假设的条件”。一次围绕一个主要判断，保留其他条件尽量可比。例如文档过期与重复录入可能同时存在，不能用一次换模型宣称验证两者。

发现多个原因时，区分**本轮主假设**和**备选后续改动**。优先验证阻断安全使用或主要业务价值的一个机制；其他问题可记录或做低投入观察，不默认在同一有限预算里连续启动第二条修复线。若确需分阶段，应分别说明进入条件、比较方式及剩余投入，不能把两项改动后的综合改善归因于其中一项。

将日志、失败样本、反馈与推断分开。不要把“员工不用”直接归为态度问题，或把“回答错误”直接归为模型太弱。必要时先完成低投入调查。

## 最终交付结构

标题：**AI 小项目行动方案**。独立可读，不依赖用户翻回前面问答补齐条件。

开头先给建议状态和最近一步行动，再按复杂度组织下列内容。以下是内容覆盖要求，不是必须逐个出现的九个标题；相关项可合并，事实和约束说明一次即可。保持影响启动、验收和停止的条件清楚，不为缩短而删去。

1. **当前建议状态**：路径、依据、关键未知，什么会改变判断。
2. **问题与现有流程**：使用者、触发事件、步骤、卡点、影响；事实与推测分开。
3. **优先切入点及理由**：与其他环节比较；已有项目列诊断假设。
4. **职责分工**：步骤与人、AI、普通程序的职责，谁接异常。
5. **第一版范围、数据和关键依赖**：输入输出、排除项、材料使用条件、技术能力方向、任务先后依赖。
6. **负责人及投入边界**：确认者、执行者、时间/费用/工时上限；估算注明依据和不确定性。
7. **验收与后续决策**：主要指标、质量与投入约束、比较方法、样本、评价人、局限及四类后续结论。
8. **未确认假设**：哪些会改变路径或阻止启动，由谁如何核实。
9. **下一步行动**：按依赖顺序给动作；属于建议，不自动开展项目。

按结论调整篇幅。补基础可只写整理材料、责任与完成判据；暂缓可只写原因和重启条件；证据不足可只写核实任务与暂定方向。不强行制造 AI 试点。用户未要求文件时在对话里交付即可。
